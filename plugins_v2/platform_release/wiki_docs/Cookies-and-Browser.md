# Cookie 同步与浏览器服务

本章包括两项不同的功能：

- **Cookie 服务：** 把浏览器中已登录网站的 Cookie 同步到系统，供已获授权的插件读取。
- **浏览器仿真：** 插件需要打开真实网页、执行 JavaScript 或进行页面交互时，使用 Chromium 或 CloakBrowser。

同步 Cookie 不会自动安装浏览器，选择浏览器也不会自动让所有网站登录成功。具体登录、验证和签到流程仍由插件实现。

## 1. Cookie 是什么，要注意什么？

Cookie 是网站保存在浏览器中的一类数据，经常包含登录状态。拿到有效 Cookie 的人可能在不输入密码的情况下访问你的账号。

因此：

- 不要把 Cookie、CookieCloud 加密密码或同步凭据发到公开群、issue、日志截图里。
- 尽量只同步插件需要的网站，避免把整个日常浏览器的所有网站登录状态都交给系统。
- 管理网页和 CookieCloud 地址尽量使用 HTTPS。不要把登录凭据通过未加密公网 HTTP 传输。
- 系统按插件声明/授权的域名提供 Cookie，插件仍然必须来自可信来源。

## 2. 选“浏览器直连”还是“远程 CookieCloud”？

| 你的情况 | 选择 |
| --- | --- |
| 还没有 CookieCloud 服务器，希望直接同步到 AWBotNest | 浏览器直连 |
| 已经有一个 CookieCloud 服务器，浏览器正在往那里上传 | 远程 CookieCloud |
| 想两个来源一起使用 | 支持，但最后完成的一次同步会替换系统 Cookie 数据；建议先只选一个来源 |

这两个区域没有必须先开启的总开关。**直连填好 UUID 与密码即可使用；远程地址、UUID、密码完整并保存后，按间隔自动同步。** 远程配置不依赖直连区域先生成凭据。

![Cookie 服务演示界面](https://raw.githubusercontent.com/wiki/AWdress/AWBotNest/images/cookies.jpg)

> 当前版本界面里“系统加密保存”和“更换凭据会清除旧数据”等提示与实现不一致。实际配置与 Cookie 是明文文件保存；生成新凭据会立即生效，但不会清空旧 Cookie。请以本章说明为准，保护好数据目录和备份。

## 3. 浏览器直连：推荐的新手配置步骤

### 3.1 安装 CookieCloud 扩展

在你平时登录目标网站的桌面浏览器中安装 [CookieCloud 官方项目提供的扩展](https://github.com/easychen/CookieCloud)。请核对发布来源，不要安装名字相似但来源不明的扩展。

扩展负责从**这个浏览器**读取 Cookie 并上传。服务器不会远程读取你手机或电脑浏览器里的 Cookie。

### 3.2 在系统生成连接凭据

1. 打开「系统设置 → Cookie 服务」。
2. 在「浏览器直连」点击「重新生成凭据」。首次没有凭据时也使用此按钮。
3. 记录界面提供的三项：

| 系统字段 | 在扩展中对应填写 |
| --- | --- |
| 服务器地址 | CookieCloud 服务器地址 |
| 用户 KEY · UUID | 用户 KEY / UUID |
| 端到端加密密码 | 加密密码 |

4. 将这三项填进扩展，**工作模式选择“上传到服务器”**。
5. 系统中的「加密算法」与扩展算法保持一致。可选 AES-128-CBC（固定 IV）和 CryptoJS（兼容模式）；不要只改一边。
6. 检查并保存系统设置、扩展设置。

系统给出的直连地址末尾为 `/cookiecloud`，例如：

```text
https://你的系统域名/cookiecloud
```

这是示意。复制你自己页面中的实际地址，不要额外拼上 `/get/UUID`。

> “重新生成凭据”会立即更换系统保存的 UUID 和密码，不是刷新按钮。已有同步正在使用时，更换后必须同步修改扩展配置。旧 Cookie 不会因此自动清空；看到旧同步数据，不代表新凭据已经上传成功。

### 3.3 让浏览器上传一次

1. 在装有扩展的这个浏览器中登录插件需要的网站。
2. 在 CookieCloud 扩展中按需设置同步域名与自动上传间隔。界面名称以扩展版本为准。
3. 使用扩展提供的同步/上传操作，或等待它的自动上传间隔。
4. 回系统查看「同步状态」，点击「检查状态」。

**成功现象：** 页面能看到最近同步时间、域名数量、Cookie 数量；下方同步记录和运行日志有结果。仅“凭据已保存”不代表浏览器已经上传。

扩展只能在浏览器和扩展运行时按其规则上传。电脑关机、浏览器关闭或扩展停用后，不能指望它继续定时更新。直连同步间隔在扩展中配置，不是远程 CookieCloud 的间隔。

## 4. 远程 CookieCloud：复用已有服务器

如果已有 CookieCloud 服务，不用搬走它，也不用让浏览器改为直接上传到 AWBotNest。

1. 打开「系统设置 → Cookie 服务 → 远程 CookieCloud」。
2. 填「远程服务器地址」：填写现有 CookieCloud 的**服务根地址**。如果服务部署在 `/cookiecloud` 子路径，应保留该子路径，但不要附加 `/get/UUID`。
3. 填「远程用户 KEY · UUID」和「远程端到端加密密码」，必须与浏览器扩展/远程服务现有配置一致。
4. 「远程加密算法」先选「自动识别（推荐）」；确知加密格式时可以固定。
5. 选择「自动同步间隔」，界面提供每 5 分钟至每天的选项。
6. 按需填「同步域名白名单（可空）」，如 `example.com, *.example.org`。多个用逗号或空格分隔；留空会同步远程的全部域名，不是“不同步”。
7. 保存设置。填写完整后会注册自动同步；要马上验证，点击「立即同步」。有未保存改动时，此按钮会先保存再执行。
8. 查看同步状态、域名和下方记录。

**正常现象：** 提示“远程 CookieCloud 同步完成”，状态显示同步数据和时间。后续系统按保存的间隔拉取，不需要每次打开网页。

远程地址、UUID 和密码保存在系统配置中，不会作为正常 Cookie 读取接口的返回值提供给插件。**网页掩码不代表磁盘文件已加密**；系统配置和解密后的 Cookie 文件都需要按敏感资料保护。

系统先尝试本地解密；失败时，可能把加密密码发送给远程服务，请求兼容解密。务必使用可信的 HTTPS 服务，不要向不可信服务提交自己的同步密码。

如果不想继续自动拉取，可以清空远程必填连接项并保存。仅关闭网页不会停止后台同步。

### 同时使用直连和远程会发生什么？

两种来源都可写入同一个 Cookie 存储。一次同步不是把所有来源无限累加，而是由最后完成的同步替换数据。如果两个来源的域名不一样，就可能出现“刚同步后有，另一边同步后又没了”。新手建议只保留一个主要来源。

## 5. “检查状态”和“清空数据”分别做什么？

- **检查状态：** 检查系统当前保存的 Cookie 及数量，不会让你的电脑浏览器立即上传，也不等同于验证每个网站的登录有效性。
- **立即同步：** 主动从已保存的远程 CookieCloud 拉取一次。
- **清空数据：** 删除系统保存的 Cookie，插件会暂时无法读取。不会替你退出电脑浏览器中的网站；下一次同步可以重新写入。

某个网站仍提示未登录时，即使系统显示有很多 Cookie，也要检查对应域名是否真的同步、Cookie 是否过期、插件是否被授权访问该域名。

## 6. 为什么插件读不到已经同步的 Cookie？

按这个顺序排查：

1. **来源是否真的上传/拉取成功？** 看最近同步时间和错误，而不是只看“设置已保存”。
2. **域名对不对？** `example.com`、`www.example.com` 和其他子域名可能涉及不同 Cookie；远程白名单也可能过滤掉目标。
3. **浏览器是否在正确的网站账号登录？** Cookie 来自扩展所在浏览器，不是任意设备。
4. **插件有没有使用系统 Cookie 接口？** 未适配的插件可能仍要求自己填写 Cookie。
5. **插件有没有声明所需域名权限？** 系统不会把所有 Cookie 无条件交给每个插件，需要开发者适配。
6. **Cookie 有没有失效？** 网站退出、修改密码、撤销会话或风控后，旧 Cookie 可能不再有效。重新登录网站并同步。

域名授权和开发接口见 [插件开发](Plugin-Development)。

## 7. 浏览器仿真：Chromium 与 CloakBrowser

入口：「系统设置 → 运行环境 → 浏览器仿真」。

![浏览器仿真与 CloakBrowser 版本演示](https://raw.githubusercontent.com/wiki/AWdress/AWBotNest/images/browser.jpg)

| 选择 | 用途 | 新手建议 |
| --- | --- | --- |
| Chromium | 默认浏览器引擎，用于普通网页自动化 | 没有特殊需求先保持默认 |
| CloakBrowser | 插件需要使用 CloakBrowser 的浏览器能力时使用 | 根据插件要求选择，不是选了就保证绕过所有验证 |

这个选择决定**调用系统浏览器服务**时的默认引擎，不会改写插件业务逻辑。插件如果明确直接使用自己指定的浏览器库、浏览器参数或外部服务，系统选择不会把它强制替换成另一个实现。

因此“系统选 Chromium，但某插件仍下载/启动 CloakBrowser”并不能单独证明选择失效：先看插件是否主动使用了 CloakBrowser。

### 第一次选择 CloakBrowser

1. 选择「CloakBrowser」。
2. 按第 8 节决定是否使用免费 Key。
3. 保存设置，等待依赖安装成功；不要重复点保存或同时重启。
4. 按插件实际功能测试浏览器调用。

CloakBrowser 不预打包进镜像；系统将 Python 依赖安装到持久化插件依赖目录。浏览器内核和 GeoIP 数据可能在真正启动相应功能时再下载。看到安装完成不代表已经下载了所有可能的浏览器资源。

## 8. 免费 Key 开关、删除 Key 和旧版回退

界面提供「使用免费 Key 获取最新版」开关以及「CloakBrowser License Key」。

| 设置 | 实际行为 |
| --- | --- |
| 开关打开，并且保存有效 Key | 向 CloakBrowser 提供这个 Key，使用有 Key 的新版内核逻辑，启用免费单会话排队 |
| 开关关闭 | 不向 CloakBrowser 提供已保存的 Key，改用无 Key 的旧版免费内核逻辑 |
| Key 删除或未填写 | 不启用有 Key 的新版逻辑，也不启用该免费 Key 单会话队列 |

使用新版免费内核的步骤：

1. 在 [CloakBrowser 免费 Key 页面](https://cloakbrowser.dev/free) 按官方要求登录并申请 Key。
2. 选择系统的 CloakBrowser 引擎。
3. 打开「使用免费 Key 获取最新版」。
4. 将完整 Key 填入「CloakBrowser License Key」，然后保存。
5. 保存成功后查看状态，确认“免费 Key 单会话排队已开启”。官方套餐政策以 CloakBrowser 当前说明为准。

不需要修改 Compose，也不需要在每个插件配置中重复填写系统 Key。本系统以保存的设置为准，不把 Docker/Compose 的 `CLOAKBROWSER_LICENSE_KEY` 环境变量当作这里的替代来源。

曾用过 Key、后来关闭或删除时，系统不会因为缓存中有新内核就强行继续使用它。无 Key 模式会选旧版免费内核；旧版尚未下载时可能需要首次下载。不要为了切换而直接删整个缓存目录。

## 9. 多个插件怎样共用免费单会话？

CloakBrowser 免费 Key 限制为一个活跃浏览器会话。系统接入的同步/异步启动会排队：前一个会话正常关闭后，后一个再启动，避免多个插件一起争用免费名额。

另外，调用**系统浏览器服务**的任务本身共用执行名额，超过名额会等待，而不是因名额暂时占用直接跳过。等待名额不消耗系统为该次调用保留的执行预算；轮到执行后，实际执行超时仍然有效。管理员停用、取消以及插件自己设置的超时仍可能终止任务。

注意边界：

- 正常关闭 `browser.close()` 或 `context.close()` 才能及时释放对应会话，插件开发者仍要正确清理资源。
- 强杀、进程崩溃或网络异常可能让官方暂时保留会话，系统可能显示异常会话释放等待；不要连续强制重启试图抢占。
- 同一 Key 在另一台服务器、另一套系统或你自己的脚本中使用，不受这台系统的进程内队列控制，仍可能触发官方会话限制。
- 排队不等于保证永久执行。插件显式取消/超时、系统停止、官方拒绝或任务本身出错，都可能结束这次任务。

任务运行情况和等待阶段可到“运行概览”的定时任务区域及“运行日志”中查看。不要看到“等待”就直接认为定时任务没触发。

## 10. “组件版本”和“内核版本”是两回事

| 页面显示 | 代表什么 |
| --- | --- |
| 组件，例如 `0.5.x` | Python 的 `cloakbrowser` 包，负责启动、下载等逻辑 |
| Stable 内核 / Preview 内核，例如 `15x…` | 真正打开网页的浏览器程序版本，可能有不同通道 |
| 免费内核 | 无 Key 模式实际可用的旧版免费浏览器 |
| 尚未下载 | 依赖可能已装好，但这个模式的浏览器内核还没下载 |

不能用组件 `0.5.x` 和内核 `152…` 比大小。它们不是同一套版本号。某插件用 Preview、另一个用 Stable，也可能出现多个内核，系统会按实际使用通道显示和处理。

### 后台检查与手动更新

- CloakBrowser：系统启动时检查一次，之后**每 24 小时**后台检查。仅在选择 CloakBrowser、免费 Key 开启且已保存 Key 时进行；无 Key 或关闭时不做该自动检查。
- 这里只是检查，不会看到有新内核就擅自把所有通道全部下载。
- 点击「检查并更新」会检查组件以及**启用插件实际需要**的内核通道，并执行更新。当前兼容范围内有新组件时，组件也会更新，不只是更新浏览器内核。
- 浏览器正在运行、排队或维护时，按钮可能暂时不可用，先等正在进行的调用结束。
- 所需版本都已满足时，按钮显示「已是最新」。这表示当前检查范围内已是最新，不等于不受兼容版本范围约束。
- 更新依赖后系统可能自动重启，页面会提示。不要在关键插件任务执行中反复点更新。

**这与 AWBotNest 自身每小时检查新版本是不同任务。** 系统版本更新见 [备份与维护](Maintenance)。

## 11. 下载目录、旧版清理与代理

Docker 常见持久化位置：

```text
/app/data/plugin_deps/    Python 插件依赖和 CloakBrowser 组件
/app/data/cloakbrowser/  浏览器内核、版本标记和 GeoIP 等缓存
```

对应宿主机位置取决于你把 `data/` 挂载到哪里，不能直接把容器路径当作宿主机路径操作。

同一环境先出现“依赖安装”，后出现几百 MB 的“内核下载”，通常是两个不同步骤；还可能因为实际需要 Stable/Preview 不同通道而下载另一内核。需结合完整路径和版本判断，不要只按“出现下载字样”认定重复下载。

手动更新成功且新版本校验可用后，系统会保守清理不再引用的旧 Pro 内核；不会在仅检查、失败或不确定安全时随意删除。当前通道引用、运行中内核、固定版本、无 Key 旧免费内核、元数据和 GeoIP 等会保留。**不是把所有旧目录一概清空。**

启用系统运行代理时，接入的组件、内核及相关资源下载会使用对应代理支持；插件明确传入的网络参数优先。代理不可用、pip 镜像滞后或官方资源网络故障都可能影响安装/更新。pip 镜像源只影响 Python 包，不会把所有内核下载变成从该 pip 镜像下载。

## 12. 常见问题速查

| 现象 | 检查方法 |
| --- | --- |
| `geoip2 is required for geoip=True` | 当前系统安装要求包含 GeoIP 附加依赖；先确认系统版本、依赖安装日志与持久化目录，旧安装可用「检查并更新」修复。此错误本身不能证明只是 ARM 问题 |
| 组件已安装，第一次插件仍下载浏览器 | 组件、内核、GeoIP 是不同资源，核对下载路径和通道；首次使用可能正常下载 |
| 已下载 Stable，插件又下 Preview | 插件需要的通道不同，不是同一个版本重复下载 |
| 关闭 Key 后提示需要下载旧版 | 无 Key 模式不能直接使用缓存的新内核；旧版尚未缓存时会下载 |
| 有 Key 却提示会话已占用 | 检查同 Key 是否在其他机器使用、前次是否强杀、当前是否有运行或等待会话 |
| Cookie 数量正常，插件仍未登录 | 检查目标域名、Cookie 有效期、插件域名权限与是否使用系统 Cookie 服务 |
| 直连一直没有同步数据 | 扩展模式是否为上传到服务器、地址能否从浏览器访问、凭据和算法是否一致、浏览器是否运行 |
| 远程同步失败 | 地址是否是根路径、UUID/密码是否配套、算法和 HTTPS、系统服务器/代理能否访问远程 |
| 重建容器后又下载 | 检查 `data/` 是否正确挂载并保留，不能只持久化配置文件而漏掉依赖/缓存目录 |

仍无法定位时，提供系统版本、AMD64/ARM64 架构、部署方式、组件/内核版本以及脱敏安装日志，见 [故障排查](Troubleshooting)。不要提交完整 Key 或 Cookie。
