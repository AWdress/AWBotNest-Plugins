# 常见问题与故障排查

先看错误出现在哪一步，再查对应部分。不要一遇到问题就删除账号、清空数据或重新安装，这些操作可能让原本容易定位的问题变成数据恢复问题。

本页命令中的容器名是默认的 `AWBotNest_V2`。改过容器名、端口或目录的，请换成自己的实际值。涉及密钥、会话、Cookie 的文件，不要上传到公开 issue。

## 1. 提问前先收集什么

建议提供以下信息：

1. 系统版本，例如 `v2.0.1.6`。
2. Docker 还是源码运行；AMD64 还是 ARM64。
3. 问题发生的具体时间、操作步骤、预期结果和实际结果。
4. 对应时段的脱敏日志；插件问题另附插件名称和版本。
5. 若是网页显示问题，附完整界面截图、手机/电脑型号与浏览器，说明是否从主屏幕 PWA 打开。

查看最近容器日志：

```bash
docker logs --tail 150 AWBotNest_V2
```

截图前遮住手机号、用户名中的隐私、Bot Token、API_HASH、API Key、代理密码、Cookie 和验证码。不要提供完整 `config.json`、`sessions`、配置包或完整备份。

系统会处理常见敏感日志，但第三方插件可以输出任意内容，不能因此省略人工检查。

## 2. 网页打不开、端口连接失败

### 先看容器是否运行

```bash
docker ps -a --filter name=AWBotNest_V2
docker logs --tail 100 AWBotNest_V2
```

- 显示 `Up`：容器在运行，继续检查地址、端口和网络。
- 显示 `Restarting` 或 `Exited`：先看启动错误，不要只刷新浏览器。
- 没有结果：核对容器名，或者执行 `docker ps -a` 找到实际名称。

### 分清两种网络模式

| 部署方式 | 浏览器应该访问哪里 |
| --- | --- |
| bridge，映射 `19001:18001` | `http://服务器IP:19001`，不是右边的 `18001` |
| host，系统监听 `19001` | `http://服务器IP:19001`，没有额外端口映射 |
| 已配置 HTTPS 反向代理 | 先用实际域名访问，再分别排查反代和后端 |

默认 bridge 配置没有特别改动时，访问端口是 `18001`。完整端口示例见 [安装与部署](Installation)。

还要检查：

- 云服务器安全组、系统防火墙是否放行相应端口。
- 是否错误使用了安装脚本显示的内网 IP。
- 端口是否已被其他程序占用。
- 是否仅改了网页监听端口，却没有同步处理 Compose 映射、环境变量和健康检查。
- 是否遗漏一键安装器生成的 `docker-compose.awbotnest-runtime.yml`，导致手动启动使用了不同配置。

不要为了排错直接关闭全部防火墙。

### IP 能打开，域名打不开或日志不刷新

优先检查反向代理：上游地址和端口、HTTPS 证书、路径转发、WebSocket 支持。

尤其注意：反向代理也在独立 Docker 容器内时，它的 `127.0.0.1` 通常不是 AWBotNest 所在容器，也不是宿主机。不能因为两者在同一台服务器，就把两个容器里的 localhost 当成同一个地址。

网页能显示但 API 报 `502`、运行日志不实时更新，仍可能是反代配置问题。不要只用“首页打开了”判断转发全部正常。

## 3. 管理员无法登录或忘记密码

### 提示用户名或密码错误

先确认：

- 输入的是 AWBotNest 网页管理员账号，不是 Telegram 账号、服务器账号或 Bot 用户名。
- 大小写、输入法、前后空格是否正确。
- 是否访问了另一套实例或另一端口。
- 最近是否导入其他实例的配置包，管理员凭据随配置改变。

仍有已登录页面时，可以到“系统设置 → 账号与凭据”修改登录凭据，但此操作需要填写当前密码。修改密码会轮换管理令牌，其他旧登录可能需要重新登录。

### 显示“管理令牌无效”

网页保留的登录状态可能已经失效，例如管理员更换密码、轮换令牌或导入配置后。先重新登录；不要把开放 API Key 当成网页管理令牌。

### 忘记密码，但你拥有服务器管理权限

当前 V2 的管理员密码摘要保存在 `data/config.json`，没有可替代此配置的独立 `auth.json` 密码文件。**不要删除整个配置文件来重置密码。**

以下方法仅供系统所有者或获授权的服务器管理员使用：

1. 先通过防火墙、反向代理访问限制等方式，让初始化期间只有你能访问网页。清空认证字段后，不能把初始化入口敞开给其他人。
2. 停止 AWBotNest。Docker 示例：`docker stop AWBotNest_V2`。
3. 找到实际挂载的 `data/config.json`，复制一份到安全位置，使用新的备份文件名，避免覆盖旧备份。
4. 用文本编辑器打开原 `config.json`，**只将以下两个已有字段的值改为空字符串**，保留其他字段、逗号和 JSON 结构：

   ```json
   "admin_salt": "",
   "admin_password_hash": ""
   ```

   这只是字段片段，不是让你用这两行替换整个文件。不要手工填明文密码到 `admin_password_hash`。

5. 保存后启动容器：`docker start AWBotNest_V2`。
6. 打开自己的网页，应出现“首次使用 · 设置管理员账号”，立即设置新用户名和强密码。
7. 确认登录正常后，再恢复原有的网络访问规则。

如果启动提示 JSON 解析错误，停止系统，恢复刚才备份的原文件，再检查编辑操作。没有服务器文件管理权限时，请联系实际部署管理员；不要把配置文件发给陌生人代改。

## 4. Telegram 验证码发送失败或账号离线

### `ApiIdInvalidError`

`The api_id/api_hash combination is invalid` 表示 Telegram 不认可这组应用凭据。

1. 到 [my.telegram.org](https://my.telegram.org) 核对同一个应用的 `api_id` 和 `api_hash`。
2. 在“系统设置 → 账号与凭据 → Telegram 凭据”重新核对，不能混入 Bot Token。
3. 保存，按页面提示重启，再到“账号管理”登录。

这种错误不是验证码输错，也不能靠反复重连或换插件解决。

### 没收到验证码、验证码过期或需要密码

- 先到 Telegram 官方客户端查看服务消息，不保证每次都通过短信发送。
- 手机号要带国家码。
- 登录流程需要在 10 分钟内完成；过期后从发送验证码重新开始。
- 两步验证密码是你给 Telegram 设置的密码，不是管理员网页登录密码。
- Telegram 要求等待时，按其限制等待，不要反复点击发送。

### 网络恢复后为什么还没上线

系统对可恢复的网络断开会尝试重连，并在恢复后重新绑定相关插件。重试有等待与退避，不是断网恢复的同一瞬间必定上线。

先查看“运行日志”，区分这些情况：

| 情况 | 处理 |
| --- | --- |
| 临时网络、DNS、连接超时 | 检查服务器网络与代理，等待恢复机制重试 |
| 管理员手动“下线” | 这是明确停止指令，需要手动上线，不会强制自行恢复 |
| Telegram 会话已撤销、失效 | 重新完成登录，普通重连不能恢复被撤销的授权 |
| API_ID/API_HASH、Bot Token 无效 | 修正对应凭据，按提示保存/重启 |
| 代理一直不可用 | 先修代理，重连不能替代可用网络 |

用户账号与 Bot 通知不是同一条连接。用户账号离线时，若 Bot 和明确的 Chat ID 都有效，通知仍可发送。若通知也失败，核对目标是否先启动过 Bot、群组/频道权限、Chat ID、Token 和投递日志。

详细步骤见 [账号与通知](Accounts-and-Notifications)。不要通过反复删除账号来处理短暂网络波动。

## 5. 插件装好了但不运行、定时时间到了没反应

先看 [插件管理](Plugins) 中的启用、配置和账号绑定步骤。下载插件不等于启用插件；需要用户账号的插件，也不能只配一个 Bot 就运行。

排查顺序：

1. 插件是否启用，配置是否已保存。
2. 需要的账号、Cookie、AI 或通知服务是否可用。
3. 到“运行概览”的定时任务区域，查看是否注册了任务、下次执行时间和当前进度。
4. 查看该插件日志，区分“没有触发”“正在等待”“开始后报错”。

### “等待浏览器执行名额”是没触发吗

不是。使用系统公共浏览器服务的任务共用执行名额：已有任务占用时，后来的任务按顺序等待，不因为名额暂时用满就直接跳过。该等待不消耗系统自有的插件执行预算；轮到执行后，实际执行超时仍有效。

插件主动取消、管理员停用、系统停止，以及插件自行设置的超时仍可能结束任务。这一机制不会改写第三方插件独立创建的浏览器或超时逻辑。

### “上次执行尚未结束，等待补跑”又是什么

这是**同一个定时任务**上一次还没结束，又到了下一次触发时间。系统避免它重叠运行，会保留补跑；多次触发会合并，不是无限累积一份历史任务队列。

默认允许延迟为 300 秒，超过允许延迟会写“定时任务跳过”并注明原因。因此：

- 公共浏览器排队，与同一 Cron 任务重入不是同一个机制。
- 排队保护不等于系统关闭期间错过的每一次任务都会重新执行。
- 看到明确“跳过”日志时，应连同前一轮开始、结束日志一起提供，不能只截某一条。

系统托管调度器按 `Asia/Shanghai`（北京时间）安排。插件自己实现的外部调度或自定义线程，不一定走此调度器；涉及插件自身逻辑时需由插件开发者排查。

## 6. AI 生图能用，但文字失败或调用很慢

图片接口和文字接口不同。生图成功，只证明对应图片请求可用，不能证明 Chat Completions、Responses 或 Anthropic Messages 都可用。

到“系统设置 → AI 服务 → 最近调用”，先看实际模型、协议、状态码、错误分类和耗时，再按 [AI 服务](AI-Service) 的步骤排查。

| 现象 | 优先检查 |
| --- | --- |
| `401` / 认证失败 | Key 是否有效，是否属于当前服务地址 |
| `403` / 权限拒绝 | 模型、账户或地区权限 |
| `404` | API 根地址、路径前缀、协议是否正确 |
| `429` | 服务商限流、额度或余额限制，以其返回说明为准 |
| HTML / `JSONDecodeError` / 协议不匹配 | 是否填成官网或登录页，是否被网关拦截，是否用了不兼容格式 |
| 超时 | 网络/代理、上游生成速度、并发等待、输入大小和插件执行时限 |

建议先只保留“一家服务、一个文字模型、一个默认模型分工”的最小配置，发一个短测试请求，成功后再加备用模型。

- “自动识别”会在符合协议不匹配条件时尝试候选格式，不代表认证失败、限流等任何错误都会换协议重试。
- 固定格式应依据服务商实际接口，不凭模型名字猜。
- 系统调用当前需要非空 API Key；本地服务不验证 Key，也不代表系统配置可以直接留空调用。
- 一次尝试的耗时可能包含并发等待、网络和服务商处理，不能仅凭总耗时断言一定是系统或模型哪一方慢。
- 增加超时是延长等待，不会加快模型。生图、备用尝试、长文本都可能比单次短文字请求慢。
- 测试是真实请求，可能计费。不要为了排错连续大量测试。

## 7. CloakBrowser 报 GeoIP 缺依赖、重复下载或版本不一致

### `geoip2 is required for geoip=True`

这表示实际运行环境缺少 GeoIP 附加依赖，不能只根据错误文字判断“只有 ARM 出问题”。当前系统的安装要求为：

```text
cloakbrowser[geoip]>=0.5.10,<0.6
```

建议：

1. 先确认系统版本、服务器架构和完整错误日志。
2. 到“系统设置 → 运行环境”，确认已选择并保存 CloakBrowser。
3. 等待安装完成，查看依赖安装日志；已有旧环境可通过页面“检查并更新”重新检查兼容组件。
4. 仍报错时，提供依赖安装结果、插件名称和插件版本，检查插件是否使用了它自己的独立环境。

不要只在运行中的容器随手 `pip install` 后就认为永久修复；未写入持久化依赖位置的内容可能在容器重建后丢失。不要随意升级成系统当前不兼容的组件大版本。

### 为什么已经安装，还会下载几百 MB

先看日志下载的是哪一种：

- Python 组件：`cloakbrowser` 及其依赖。
- 浏览器内核：真正的 Chromium 程序，可能有 Stable、Preview 或无 Key 免费内核。
- GeoIP 等资源：功能所需的额外数据库。

这三者不是同一个下载。同一个插件明确需要另一个通道，或者关闭 Key 后首次使用旧免费内核，可能发生新的正常下载。具体目录和版本说明见 [Cookie 与浏览器](Cookies-and-Browser)。

若每次重建容器都重新下载，先核对 `data` 挂载和缓存路径；不要只持久化一个 `config.json` 而漏掉其余目录。

### 组件是 `0.5.x`，插件却说浏览器是 `152…`

一个是 Python 组件版本，一个是内核版本，本来就不能相互比较。“已是最新”也指当前兼容范围及实际所需通道，不代表所有通道都已下载。

免费 Key 开启、删除、单会话等待和旧内核回退，见 [Cookie 与浏览器](Cookies-and-Browser)。不要公开 Key，也不要直接删除整个缓存目录作为第一步。

## 8. 内存很高、系统突然重新初始化

“重新初始化”只说明服务重新启动，不足以证明是管理员点击了重启，也不能直接归因于 Telegram 重连。

先执行：

```bash
docker stats AWBotNest_V2 --no-stream
docker top AWBotNest_V2 -eo pid,ppid,rss,comm
docker inspect AWBotNest_V2 --format 'StartedAt={{.State.StartedAt}} RestartCount={{.RestartCount}} OOMKilled={{.State.OOMKilled}}'
```

进一步检查方式见 [更新与维护](Maintenance) 的内存部分。重点判断：

- Python 主进程是否持续增长，还是浏览器运行时的短暂峰值。
- 容器内存上限是否过小，同时运行多少重型任务。
- 宿主机内核日志是否出现 `Memory cgroup out of memory` 或 `Killed process ... python`。
- 是否发生容器自动重启、主机重启或部署更新。

进程被 OOM 结束后，Docker 可能自动重启容器；重启后的 `OOMKilled=false` 不能单独排除上一轮 OOM。不要仅凭重启后的空闲内存，判断高峰时没有超限。

不要用清空日志、删插件依赖来代替内存诊断。提高额度、减少重型并行任务、修复具体插件的资源释放，需要依据进程和日志证据选择。

## 9. 点了清理日志，怎么好像没变化

先看你希望清理的是哪一种日志：

| 内容 | 网页“立即清理日志”是否处理 |
| --- | --- |
| 网页中的系统/插件共用日志历史 | 处理，按已保存的总条数保留 |
| `data/logs/app.log` 和轮转文件 | 不处理 |
| Docker 保存的容器输出日志 | 不处理 |

常见情况：

- **原来只有 200 条，设置保留 1000 条：** 没有多余记录，结果是清理 0 条。
- **只改了输入框，没有保存：** 手动清理仍按上次保存的值执行。
- **保留 100 条，清完又多一条：** 清理结果本身是一条新日志；此后系统仍会继续写日志。
- **磁盘没有明显变小：** 网页历史体积通常很小，清理并不删除文件日志和 Docker 日志。
- **没有看到结果：** 清除级别/关键词等筛选，查看系统日志中的“日志手动清理完成”或“日志自动清理完成”。失败会记录错误，不应当作清理成功。

自动清理默认每天北京时间 `03:00` 执行，默认保留 1000 条。关闭定时清理不等于禁止手动清理。详细设置见 [更新与维护](Maintenance)。

## 10. 仍然定位不了

反馈时使用这个模板即可，不要附真实敏感值：

```text
系统版本：
部署方式：Docker / 源码
架构：AMD64 / ARM64
出错时间（注明时区）：
相关插件及版本（如有）：
我做了什么：
预期结果：
实际结果：
对应时段脱敏日志：
已尝试的排查步骤：
```

如果问题只发生在某个插件，且系统服务和其他插件正常，请同时联系插件开发者。系统能提供通用服务，但无法替不兼容插件自动补全所有业务逻辑。
